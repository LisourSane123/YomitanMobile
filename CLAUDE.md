# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
# Build debug APK
./gradlew :app:assembleDebug

# Install on connected device
adb install app/build/outputs/apk/debug/app-debug.apk

# Run all unit tests
./gradlew :app:testDebugUnitTest

# Run a single test class
./gradlew :app:testDebugUnitTest --tests "com.yomitanmobile.util.JlptLevelUtilTest"

# Build release APK (minified)
./gradlew :app:assembleRelease
```

Prerequisites: JDK 17, Android SDK 35. The build pins JDK 17 via a Gradle toolchain (`kotlin { jvmToolchain(17) }` in `app/build.gradle.kts`), which Gradle locates automatically — no machine-specific path in the committed `gradle.properties`. If your default `java` is older than 17 and the toolchain can't find a JDK 17, set `org.gradle.java.home` in your user-level `~/.gradle/gradle.properties`.

## Architecture

Clean architecture in three layers: `data/`, `domain/`, `ui/`, wired together with Hilt DI.

### Domain layer (`domain/`)
- `model/` — pure Kotlin data classes: `WordEntry` (raw DB entry), `MergedWordEntry` (grouped search result), `AnkiCard`, `CardStylePreferences`
- `repository/DictionaryRepository.kt` — interface; the single abstraction boundary between data and domain
- `usecase/` — `SearchDictionaryUseCase`, `GetWordDetailUseCase`, `DictionaryManagementUseCases`

### Data layer (`data/`)
- **Room** (`data/local/`): `AppDatabase` at version 22 with migrations defined inline (6→22; there is no path from 1–5, accepted because `versionCode = 1`). Favourites and search history are per-language *in their unique indexes too* (`(expression, reading, language)` / `(query, language)`, migration 19→20) — the language column alone was not enough, because both DAOs insert with REPLACE and a shared spelling then deleted the other language's row. Tables: `DictionaryEntry` (FTS-enabled via `DictionaryEntryFts`), `DictionaryInfo`, `ExportedWord`, `FavoriteWord`, `SearchHistory`, `KanjiEntry`, `Sentence`, `LookupCount`, `WordFrequency`, `FrequencyListSetting`, `JlptTag`, `AnkiCollectionWord`. Complex columns (lists, JSON) use `Converters.kt`.
- **Parser** (`data/parser/YomitanDictionaryParser`): streaming ZIP parser for Yomitan/Yomichan dictionary format. ZIP contains `index.json` + `term_bank_N.json` files. Handles both term dictionaries and meta dictionaries (frequency/pitch data).
- **Repository** (`data/repository/DictionaryRepositoryImpl`): delegates search to `DictionaryDao` which uses FTS for expression/reading and a separate path for EN definition search.
- **Anki note type** — one, forever: a refused template write used to mint `Yomitan-Mobile-v8-1`, `-2`… on every export, and one real collection ended up with 1 113 of them, 1 029 holding a single note. `getOrCreateModel` now prefers a compatible model whose templates ALREADY match (read back through the provider, so no write is attempted), and when a write is refused it keeps exporting to that model — the cards render with the previous layout, which beats a note type per card. A new model is only created when the collection has none with this profile's fields.
- **Anki** (`data/anki/AnkiCardCreator`): integrates with AnkiDroid via `AddContentApi`. Anki model name is `Yomitan-Mobile-v8` (stable — do not bump unless `FIELD_NAMES` changes). Fields: `Front`, `FrontContext`, `Reading`, `Meaning`, `PitchAccent`, `Frequency`, `Audio`, `Sentence`, `KanjiBreakdown`, `Summary`. `Frequency` holds the **raw frequency rank as a plain number** ("4821"), empty when no frequency dictionary ranks the word. It renders in the card's top-right corner when the `showFrequency` preference is on (off by default); the element is always emitted and CSS decides visibility, because the other way round — a CSS rule with nothing producing the element — is what made that preference a switch wired to nothing. Anki itself is the other consumer (addons like AutoReorder sort new cards by it and need a sortable number). The starred tier label (`frequencyLabel()`, `Top 1K`…) is a UI-only thing for the search and detail screens — do not put it back on the card. `exportBatchToAnki()` is the bulk path used by the JLPT deck generator: it resolves model/deck/CSS once and writes through `addNotes` in chunks of 50, with no AI summaries and audio only on request.
- **Card engine** (`data/anki/MonolingualCardResolver`): switches the Meaning field between JP-EN and JP-JP. Sits between "what the search found" and "what gets written", so the detail-screen export and the JLPT batch share it. Rules: definition from the dictionary named in `CARD_MONOLINGUAL_DICTIONARY`; words missing from it keep their English gloss (a monolingual dictionary covers far fewer headwords, and a blank back is worse); example sentences stay but lose their English translation. The dictionary is chosen from the *installed* list, never hardcoded — the commercial 国語辞典 (三省堂, 明鏡, 新明解…) are only distributed on Drive/Mega and cannot be shipped as downloads, so users import their own zip; `日本語 Wiktionary` is offered as the freely licensed one-tap option.
- **Anki duplicate scan** (`data/anki/AnkiCollectionIndex` + `AnkiNoteFieldIndexer` + `KanaSpellingVariants`): reads the whole AnkiDroid collection through `FlashCardsContract.Note` (selection = Anki search string) and indexes every short, purely-Japanese field value. Note-type agnostic on purpose, so it matches Core 2k/6k/10k, Kaishi 1.5k and hand-rolled note types without per-deck field mappings. A field is first cut into pieces on block markup (`<br>`, `<div>`) and list separators (`;`, `/`, `|`, newline) — a field holding two spellings or two lines used to be glued into one nonsense run and lost entirely — and each piece is judged on its own by a raw-field ceiling (40 chars, loose because ruby carries readings inline) and a finished-key ceiling (16, the real headword limit). `漢字[かんじ]` ruby fields are indexed under the expression, the reading AND the mixed spellings in between (`持[も]って 来[く]る` → 持って来る, 持ってくる, もってくる), because that is where decks disagree with JMdict. What separates a ruby headword from a ruby SENTENCE is no longer a run count: Anki only ever spaces before a kanji-reading group, so a kana-only run in the middle (`私[わたし] は 毎日[まいにち] …`) means words were spaced apart by hand, while `落[お]ち 着[つ]き 払[はら]う` is one word — counting runs threw away every three-block compound along with the sentences. On the lookup side `Index.containsAny()` takes ALL of an entry's written forms and, from the reading, the mixed kanji/kana spellings of each (持って来る ↔ 持ってくる); a bare reading match stays restricted to kana-only / `uk` words, since 聞く must not match a collection holding きく. **The word count is not a card count and never will be**: one note yields both its written form and its reading, and one note can back several cards, so words > notes > cards is the expected shape, not a bug. Degrades to "unavailable" (never to false positives) when the provider can't be read.
- **Stored collection scan** (`data/anki/AnkiCollectionStore` + `anki_collection_words`): the scan is seconds of provider work, so it runs on demand from `AnkiScanScreen` and the result is persisted. Every duplicate check afterwards — mining (`DetailEvent.AlreadyInCollection`) and the JLPT generator — reads the stored copy. An empty store means "not scanned", never "you have nothing", so a missing scan can't silently swallow a card; and a failed rescan keeps the previous result rather than wiping it.
- **AI summaries** (`data/ai/`): optional, opt-in summary text on Anki exports. `AiSummaryService` talks to Gemini / DeepSeek / OpenAI against a hardcoded HTTPS host allowlist; the user supplies their own API key (header-based auth, never in the URL). The key lives in DataStore (`CARD_AI_API_KEY`) and is excluded from backups in `BackupManager` on both export and import.
- **Download** (`data/download/DictionaryDownloadManager`): validates HTTPS URLs against an allowlist before downloading; entries in `AvailableDictionaries` with a `sha256` set are checksum-verified after download. Installs run through a **queue on the application scope**, not the caller's: a dictionary takes minutes to import and the work used to die the moment the user left the download screen. `enqueue()` returns immediately, the queue installs one at a time in the order asked for, a failure does not stop the rest, and `DownloadQueueStrip` shows what is running from every tab. The install step is behind `installer` so `DownloadQueueTest` can pin the queue's behaviour — order, de-duplication, cancelling, failure — without a network. The catalogue offers two bulk buttons: the recommended bundle, and every frequency list at once (`downloadAllFrequencyLists`) — they are 1-5 MB each and all of them are read (the leading one stamps the card and orders search, the rest fill its gaps, and the text scanner reads all of them while segmenting), so "install them all and choose the leader afterwards" is the normal way to set this up. Two things keep a queue fillable, and both were broken: the catalogue's Download buttons are disabled only for what is *already queued*, never for "something is installing" (that gate meant a second dictionary could be added only after the first had finished — the moment a queue is not needed), and claiming the worker slot happens under the same lock that adds the work (`draining`, not `Job.isActive`: a worker that has just found the queue empty stays active a moment longer, and an item added in that moment waited forever). Adding to the queue happens synchronously under `queueLock` inside `enqueue()` (only the worker is launched) — adding from a launched coroutine let two quick taps land in either order. The application scope survives a screen but not a minimised app, so every `enqueue()` that adds work also starts `service/BackgroundWorkService` — a `dataSync` foreground service with a progress notification and a partial wake lock, doing no work of its own and stopping itself when the queue and `FrequencyRecomputer` are both idle. It is started only AFTER the items are in the queue, because its first look at an empty queue stops it. Setup installs through the same queue (it used to call `downloadAndImport` from its ViewModel, outside the queue and outside the service). The two-second "finished" banner no longer holds `downloadMutex` — every queued item used to pay it, and a caller arriving during it was told another download was in progress when none was.
- **Three frequency lists, one per register**: the catalogue offers JPDB (anime/manga/LN/VN, the default and the one in `recommended`), BCCWJ (formal writing) and CEJC (everyday conversation). Seven were offered once; CSJ, NWJC and Aozora Bunko were removed because only the LEADING list's numbers ever reach a card, an Anki reorder addon or a rarity cut, so every list past the first is a tiebreak for words the leader does not know. All three ship RANKS — 1 is the commonest word and the numbers climb — which is the direction the card field, the search order and the Top-N tiers all read; a count-based list added here would be detected at import and stored honestly, but would put a five-million next to a four-digit number and mean the opposite by it. A list the user wants anyway still goes in through "import dictionary from file".
- **Meta side tables** (`word_frequencies`, `jlpt_tags`): frequency ranks and JLPT levels are stored independently of the term rows, because `dictionary_entries` is deleted and re-inserted on every re-import (and a meta dictionary installed BEFORE its term dictionary has nothing to update). `DictionaryRepositoryImpl.reapplyStoredMeta()` runs `applyJlptLevelsFromTags()` + `applyFrequenciesFromTable()` after every import, so install order no longer matters. The JLPT statement only improves a row (easiest level wins, 5 = N5). Frequency is no longer "best rank anywhere": `applyFrequenciesFromTable(leadingDictionary)` takes the rank from the list the user put FIRST in the frequency priority order (`FrequencySettings.leadingDictionary()`), and falls back to the best rank elsewhere only for words that list does not know. Several lists disagree by design — a word common in conversation is rare in print — and taking the minimum let one generous list speak for all of them, on the card, in the search order and in the rarity filters of both deck generators. Changing the leading list re-runs the rollup (`DictionaryRepository.reapplyFrequencies()`) — through `FrequencyRecomputer`, which runs these passes one at a time on the application scope and exposes `isRunning`; `FrequencyDisplayScreen` covers itself with a touch-swallowing overlay while it is true, since each pass takes seconds, since the setting decides a stored column, not a display detail. `FrequencySettings.strictLeading()` ("trzymaj się tylko głównej listy", off by default) drops the fallback entirely: a word the leading list does not know stays unranked rather than borrowing a number from another scale, which is what an Anki reorder addon needs — it sorts new cards by the `Frequency` field, and two lists interleaved there order cards the way neither list meant. The leading list is also what the UI shows: `SearchViewModel.withLeadingFrequency()` stamps each result with that list's own number (one chunked query per search, `MergedWordEntry.leadingFrequency`) so the result list names the list the card will quote, while the detail screen still shows every installed list as chips with the leading one starred. A word the leading list does not know falls back to the tier label there, which is visibly a different kind of statement. **A list's numbers do not always run the same way, and are never converted**: most ship ranks (1 = commonest, ascending), some ship the raw occurrence counts they were built from (Innocent Corpus, the "word count" lists — 5 000 000 = commonest, descending), and the Yomitan meta format has no field saying which. `FrequencyDirection.isCountBased()` decides from the shape of the numbers at import, `frequency_lists` stores the answer, and the frequency screen states it per list in words ("RANKING ↑ rosnąco" / "LICZBA WYSTĄPIEŃ ↓ malejąco"). There is deliberately no user toggle and no in-place conversion any more: `word_frequencies.rank`/`display_value` hold the shipped number forever (migration 21→22 restored it for lists the old code had rewritten), and the only derived value is `word_frequencies.position` (1 = commonest, `data/local/database/FrequencyPositions`, temp table because API 26 has no window functions), used for ordering, "Top N" and rarity cuts but never shown as the list's number. The rollup writes two term-row columns: `frequency` = position (leading list's, else — unless strict — best elsewhere) and `frequency_value` = the LEADING list's number verbatim, "" when it does not know the word. `frequency_value` is what the card's `Frequency` field carries (sort ascending/descending in Anki per the list's format) and it gates every tier badge — `FrequencyTier.label(position, leadingValue)` returns "" without it, so "Top 3K" is only ever said on the leading list's authority. The leading list is `FrequencySettings.leadingDictionary(installed)`: first saved list still installed, else the first installed one — the same order the screen draws. It is set by tapping a list on the frequency screen or a chip on the detail screen. After the 21→22 migration (or restoring an older backup) `FrequencyRecomputer.ensureStorageCurrent()` runs the rollup once at app start, decided from the data (`hasFrequencyValues()`), not a flag. `FrequencyCorpus` maps an installed list's name to what it counted (JPDB → anime and visual novels, CEJC → everyday conversation), which is what the settings and download screens show. Removing this is what silently emptied the JLPT deck generator.
- **Backup** (`data/backup/BackupManager`): user-triggered folder backups (DB + whitelisted settings JSON) under `getExternalFilesDir`. WAL is checkpointed before the DB copy; restore deletes stale `-wal`/`-shm` sidecars before overwriting, and stages the incoming copy in a sibling `*.restore-tmp` file that replaces the database by `renameTo` — streaming straight onto the live file destroyed it when the copy failed half-way. Keep all three invariants if touching this code.
- **Pronunciation archive** (`data/audio/AudioArchive` + `audio_files`): the user's own folder of recordings, indexed once with a persisted SAF tree permission and queried by key afterwards — SAF cannot ask "is there a file called 食べる.mp3" without walking the tree, and these archives run to hundreds of thousands of files. TTS is the fallback, not the source: it reads a headword with no context, so it picks a plausible reading rather than the right one (行った, 一日, 開く) and flattens the pitch accent the card prints above it. Archives are not redistributable (same reason as the 国語辞典), so the user brings the folder. File naming has no standard, so `AudioKeys` reads both halves of a path and assumes nothing: 食べる.mp3, 食べる_たべる.mp3, たべる - 食べる.mp3 and 食べる/たべる.mp3 all resolve, a pair outranks a spelling outranks a bare reading. A bare reading IS matched, unlike in search — きく must not answer for 聞く in a lookup, but a homophone's recording is the right pronunciation of both. Audio now flows through `AnkiCardCreator.MediaSink`, because the two destinations differ: the provider copies the file during the call, the `.apkg` writer reads it when it zips, so `consumesImmediately` decides who may delete the temp file. "Audio wanted" is a separate question from "a TTS voice exists" — an archive needs no voice.
- **VOICEVOX voice** (`data/audio/voicevox/`): neural Japanese TTS, and the card-audio order is now archive → VOICEVOX → system TTS (`AnkiCardCreator.resolveAudio`, and the detail screen's play button after a dictionary file). Opt-in download (~155 MB: two voice models + the Open JTalk dictionary, `VoicevoxAssets`, SHA-256-pinned, through `DictionaryDownloadManager.openAllowed` so every redirect hop meets the same host allowlist) after the user accepts the voice terms in Settings; the credit they ask for (`VoicevoxAssets.CREDIT`) is shown there and in the licences dialog. The point is not only quality: `VoicevoxSpeaker` is given the READING with the entry's pitch accent written in (`AccentKana`, AquesTalk notation `ツキツケ'ル`), so the recording says what the card's pitch diagram shows instead of guessing reading and accent from a headword. Six neutral narrator voices (VOICEVOX Nemo, No.7 アナウンス — the character voices read single words with too much attitude), picked per word by hash, so a word always gets the same voice; `WavLoudness` evens them out at −18 dBFS RMS. `VoicevoxSpeaker` has no Android in it: `KindleSync` runs the same class through VOICEVOX's desktop jar, so laptop and phone cards sound alike. `VoicevoxVoice` (Android) owns the install on its own scope (leaving Settings must not cancel it), caches recordings per word, and unloads the models after a quiet minute — the synthesizer has no close(), only a finalizer, so `VoicevoxSpeaker.close()` unloads the models explicitly. The bindings are not on Maven Central: `settings.gradle.kts` fetches the release's local-Maven zip and the Android ONNX Runtime into `.voicevox/` (gitignored, SHA-256-pinned). The APK carries arm64-v8a only and compresses native libs (`useLegacyPackaging`): +9 MB instead of +52. An x86_64 emulator gets no VOICEVOX and falls back — `VoicevoxVoice.wav` catches the missing library. Model release 0.16.4 with core 0.17.0 — the pair VOICEVOX's own 0.17 downloader installs.
- **Package export** (`data/anki/ApkgWriter` + `ApkgSchema`): writes a deck as a schema-11 `.apkg` instead of through the provider. Two things it buys: the note type is exactly ours (the provider's refused-template-write path is what minted 1 113 of them), and a card can arrive **suspended** — `AddContentApi` cannot suspend anything, `cards.queue = -1` in a file we write is just a column. `ApkgSchema` holds every pure part (field checksum for Anki's duplicate finder, sort field, note-type/deck/config JSON) so the undocumented format is pinned by tests; a real `org.json` is on the test classpath because the Android stub throws on every call. Cost: a file knows nothing about the collection it lands in, so the duplicate check is only as good as it was at generation time, and the stored scan is deliberately NOT told about a written file — until it is imported, those cards exist nowhere.
- **Refreshing old cards** (`data/anki/AnkiNoteRefresher`): brings notes this app wrote earlier up to what it writes today. Two operations, because the provider allows exactly two of the three things one would want. **Restyle** rewrites templates + CSS on every note type of ours — the stray `Yomitan-Mobile-v8-N` types included, so old cards render as the current design without a note being touched. **Refresh** rebuilds note FIELDS from today's data (frequency from the list that leads now, pitch, kanji breakdown, a recording from the archive) through `AddContentApi.updateNoteFields`, which updates a note in place: same id, same deck, same scheduling. What a refresh writes is decided by `RefreshMerge`, shared with the desktop tool (`kindle-sync.sh --refresh-cards`): the fields that belong to the NOTE — `Front` (the spelling the card is known by, and its font), `FrontContext` (the mined sentence), `Summary` (an AI call per card) — are kept whenever they hold anything; a field with the user's own writing in it (Polish letters outside the app's `pos-line`/`usage-tags` labels — "źrenica" typed after a gloss) is kept whole; a tier label in `Frequency` is replaced by the rank or cleared, never kept; everything else takes the rebuild and falls back to the old value when the rebuild is empty. "Empty keeps old" alone was the rule once and it protected nothing it claimed to: the rebuild fills `FrontContext` with the dictionary's first example and `Front` with the headword in a fresh random font, so a refresh replaced the book sentence and the book's spelling. A word no installed dictionary knows is skipped entirely rather than rewritten from a blank entry. **The name decides what is ours, not the field count** — the note types most in need of a refresh are the ones this app left behind while it was being written, and they have fewer fields (no Summary, no FrontContext, no KanjiBreakdown). A lean type is adapted to rather than refused: `buildBackTemplate(..., available)` and `buildFrontTemplate(available)` name only the fields that type actually has (AnkiDroid prints an unknown `{{Field}}` verbatim), the word is taken from `Front` or else the type's first field, and fields are written BY NAME so a type without Summary simply never receives one. The name test is an exact match on the CURRENT profile's model name or that name plus a hyphen, and `STANDARD_MODEL_NAMES` refuses Anki's own note types, the shared decks (Core 2k/6k, Kaishi, Tango) and desktop Yomitan's outright — redundant against the prefix rule today, kept because that rule is the kind that gets loosened later. `OurModelsTest` pins all of it. **Merging the strays into one note type is not possible from here**: the provider cannot change a note's `mid`, and the workaround (new note, delete the old) destroys review history — desktop Anki does it in place, and that is what the UI says. It was done that way on the user's collection on 2026-09-21: AnkiConnect's `updateNoteModel` moved 1669 notes onto `Yomitan-Mobile-v8` with every card's scheduling compared equal before and after (safe only because every stray had one template and the same fields), and a one-off add-on deleted the 1144 emptied types — a schema change, so a full sync follows.
- **Card maturity** (`AnkiCollectionIndex.scanMature`, `anki_collection_words.mature`): a second provider sweep with Anki's own definition as the search string (`prop:ivl>=21 -is:suspended`). A sweep, not a per-note card lookup: the provider has no bulk card query, so asking each note for its cards is one binder round trip per note. Nothing is ever hidden on the strength of the column — an old provider and a pre-maturity scan both read as "nothing is mature", so it only ever adds a stricter number beside the existing one. It exists because "I have a card for this" and "I know this" are different claims and the app used to make the first while meaning the second.
- **Sentences**: example sentences come from two local sources only — Jitendex examples attached to each entry (with per-sense `definitionIndex`) and the pre-seeded `SentenceDao`. The former online Tatoeba fetch (`OnlineSentenceService`) was **removed**; there is no network sentence lookup and no consent flag anymore.

### UI layer (`ui/`)
MVVM with Jetpack Compose. Each screen has a paired `ViewModel`. Navigation is defined in `ui/navigation/AppNavHost.kt` with sealed `Screen` routes, wrapped by `AppScaffold`, which adds the bottom bar on the four top-level destinations (Search / Tools / Stats / Settings) and nothing else — a detail view or a deck generator is a place you finish and leave. `ToolsScreen` is the hub for everything that builds cards in bulk; those three used to be rows inside Settings, four scrolls deep.

`ui/common/` holds what every screen was copying: `LocalIsEnglish` + `tr()` / `rememberTr()` (the interface language was answered separately in fifteen screens, and threaded through helpers as an `isEnglish` parameter), `rememberAnkiPermissionGate()` (the AnkiDroid permission launcher existed four times over), and `SectionTitle` / `ToggleRow` (duplicated between the two deck generators, and already drifted by 4dp). Icons that sit beside their own label keep `contentDescription = null` on purpose — that is what makes a screen reader read the label once instead of twice.

Key screens: `SearchScreen` (main), `DetailScreen` (word details + Anki export), `DictionaryDownloadScreen`, `SetupScreen`, `FavoritesScreen`, `StatisticsScreen`, `SettingsScreen`, `CardStyleScreen`, `JlptDeckScreen`, `AnkiScanScreen` (collection scan + detected-word list), `KanjiBrowseScreen` / `KanjiDetailScreen`.

`LocalIsEnglish` is provided once in `MainActivity`. Nothing provided it for a long time, so every `tr(pl, en)` returned the default branch and an English device saw a Polish interface.

Anything a screen runs on entry must be off the main thread. `AnkiCardCreator.getAvailableDecks()` was a plain blocking provider call made from a `viewModelScope.launch` (which is `Dispatchers.Main`), and reading `deckList` opens the collection on AnkiDroid's side: the deck generator came up frozen and its back button did nothing until the provider answered. The dispatcher now lives on the function, not at the call sites.

**Kanji** (`ui/kanji/`): the browser is a join between two things the app already stored and never put together — every kanji its dictionaries describe, and every word in the stored AnkiDroid scan. Grade/JLPT/strokes/newspaper rank are read from both places a Yomitan kanji bank puts them (the tag string and the stats object) and stored on `kanji_entries` (migration 23→24); they default to 0, so a KANJIDIC imported earlier reads as "the dictionary did not say" until re-imported, and the screen tells those two states apart. Coverage is stated twice, as cards-that-exist and as mature cards, because only the second says anything about memory. One character's screen lists the words it is written in — `searchContains` with a single character in it.

**Deck review** (`ui/common/DeckPreview`): both generators list what they are about to create and let the user tick words they already know. Frequency-first ordering means the head of every generated deck is by definition what the reader has; `assumeKnownTopRank` could only cut that off by a number. Ticked cards are still created — the deck stays complete and one unsuspend brings a word back — and suspension is real only on the `.apkg` path; through the provider they carry the tag `yomitan-suspend` and the UI says so rather than pretending.

### Search pipeline
`SearchViewModel` → `SearchDictionaryUseCase` → `DictionaryRepository` → `DictionaryDao`

- **JP mode**: detects kanji/kana input, generates inflection candidates via `JapaneseDeconjugator.analyze()` (max 24, depth 3), then `invokeWithAlternatives()` runs the literal query + candidates **in parallel** (`coroutineScope` + `async`) and merges by entry ID, literal query first.
- **Substring pass**: search used to be prefix-only, so 欲 found 欲しい but never 食欲 — half of what a kanji lookup is for. `DictionaryDao.searchContains` runs in the same parallel batch and its results are appended LAST, so the word itself and its prefix matches still outrank the compounds it merely appears in. The query excludes prefix matches itself (they are the frequent rows and would otherwise eat the whole LIMIT) and matches via an `id IN (…UNION…)` subquery so the unavoidable `LIKE '%x%'` scan stays inside the small `expression`/`reading` indexes instead of pulling every `definition` blob through the page cache. `SearchDictionaryUseCase.shouldSearchSubstring` gates it: a single kanji yes, a single kana no (it would match a large share of the dictionary, per keystroke, to return noise).
- **Kana script**: an all-kana query is searched in the other script too (`util/KanaScript`, wired into `SearchDictionaryUseCase`) — こーひー finds コーヒー — and ranks with the literal query rather than behind the deconjugations, being the same word the user typed. Repeated vowels fold into ー and back (こおひい → コーヒー, ラーメン → らあめん), which is what makes romaji input reach katakana headwords. A query with kanji in it is left alone: タベル is not a spelling of 食べる.
- **EN mode**: FTS on definition text via `searchByDefinition`.
- **Romaji mode**: converts via `RomajiConverter` then searches as JP.
- Mode is auto-detected from the script per keystroke; there is deliberately NO user-facing mode toggle (the app should figure out intent itself). Romaji input is covered automatically by the EN-mode fallback, which converts the query to hiragana and merges those results in. `SearchViewModel.toggleSearchMode()` + `manualModeOverride` + the ROMAJI enum value survive as internal, tested machinery, but no UI calls them.
- Debounce is 100 ms in `SearchViewModel`; results are merged via `MergedWordEntry.mergeEntries()` which groups by `(expression, reading)` key.

### JLPT deck generator
`JlptDeckScreen` → `JlptDeckViewModel` → `JlptDeckPlanner` (pure, `domain/usecase/`) → `AnkiCardCreator.exportBatchToAnki()`.

Builds a whole JLPT level as cards without mining. Candidates are the union of dictionary entries tagged with the level (`jlpt_level` column, fed from `jlpt_tags`) and `JlptVocabulary.wordsForLevel()` resolved against the installed dictionaries. The built-in list is curated and deliberately small (844 words across all five levels), so **deck completeness comes from the `JLPT Vocab Tags` meta dictionary** (~8000 words, in `AvailableDictionaries`); when no installed dictionary tags the selected level, `JlptDeckScreen` says so upfront rather than after an empty analysis.

`JlptDeckPlanner` matches tags token by token: `MergedWordEntry.partsOfSpeech` holds one *joined* tag string per source entry ("n, v5r, arch"), not one tag per element — comparing whole strings against the tag sets matched nothing. The proper-name check prefers the entry's own tags and only falls back to the dictionary name when there are none, because a merged entry carries a single dictionary name for the whole group.

`JlptDeckPlanner` applies the filters in a fixed order (no definition → proper name → unranked → too rare → archaic → already in Anki → already mined → over limit) so each skipped word is counted exactly once and `selected + skipped == candidates`. Kept words are sorted most-frequent-first, which is also the order a capped deck keeps — and, since AnkiDroid introduces new cards in insertion order, the order the deck is studied in. Words no frequency dictionary ranks cannot join that ordering, so they go last **shuffled** (`random` is a parameter of `plan()` so tests can seed it): sorting them by expression instead put every あ-word in the first fifty cards and every わ-word in the last fifty, which is the one order a vocabulary deck must not have.

Generated cards are deliberately NOT written to `exported_words`: they aren't mined, so counting them would swamp the mining statistics. The "don't recreate what I already have" guarantee comes from the stored collection scan instead, which also covers Core/Kaishi and previously generated levels. Notes are tagged `yomitan-mobile`, `jlpt-nX`, `auto-generated` so they stay findable and bulk-deletable in Anki.

### Text scanner (subtitles / EPUB → cards)
`TextScanScreen` → `TextScanViewModel` → `TextFileReader` + `JapaneseTokenizer` → `TextScanPlanner` (pure) → `AnkiCardCreator.exportBatchToAnki()`.

Turns a file the user actually watched or read into cards for the words they don't know yet.

- **Multi-file** (`JapaneseTokenizer.Accumulator`): several files are scanned as ONE body of text (a season of subtitles, a series of volumes) — counts add up, and the first-occurrence offset comes from the earliest file. `TextScanViewModel` sorts the picked documents by file name first, which is what puts `ep01, ep02, …` in watching order; the deck name and Anki tag default to the files' common name prefix.
- **Reading** (`data/text/`): `TextExtraction` handles SRT / VTT / ASS-SSA / TXT / EPUB, `TextFileReader` owns the `Uri`/ContentResolver side and a 64 MB ceiling. Format detection is extension-first with a content sniff fallback (SAF Uris usually report `application/octet-stream`). Charset detection tries strict UTF-8 first — it is the only self-validating one of the three encodings Japanese subtitles come in — then Shift_JIS, then EUC-JP. A SHORT page (under 800 characters) carrying one publisher phrase — the colophon, the staff credits, the author's profile, the e-book notice — is skipped; 無職転生 had them on four pages of 120-285 characters and they put 発行, 株式会社, 在住, 岐阜県 and the editors' surnames into the deck. A page whose text carries three of the publisher's phrases (本電子書籍, 無断, 複製, 発行者, 著作権…) is the e-book's terms, not a scene — some publishers obfuscate the class names, and it put 電子書籍, 複製 and 発行所 into the deck. EPUB `<head>` is dropped (its `<title>` repeats the book title in every chapter file — one volume made cards of 電子/特典/付き), and so are table-of-contents, colophon and caution pages (`body class` / `epub:type`: `p-toc`, `p-colophon2`, `p-caution`, `<nav>`). EPUB chapters are read straight out of the ZIP (no `content.opf` spine parse: word extraction doesn't care about reading order), and `<rt>`/`<rp>` furigana is dropped **before** tag stripping, otherwise every reading would be tokenised as its own word.
- **Segmentation** (`util/JapaneseTokenizer`): longest-match against the installed dictionaries' written forms (`DictionaryRepository.getSurfaceLexicon()`, held in memory for the scan — hundreds of thousands of substring tests cannot go through SQLite), falling back to `JapaneseDeconjugator` so 食べました reaches 食べる instead of being chopped into 食. Deconjugation only fires for 2+ character forms ending in kana, and every surface→base decision is memoised per document. Deliberately no Kuromoji: its IPADIC is ~5 MB of data the app already has, and "longest wins" is the right bias for vocabulary lists. Four rules keep "longest wins" from inventing words, each of them measured on a real novel scan (`BookScanHarness`): **(1)** a lone kanji with a kanji neighbour is not a word — without it the heroine's name 朱音 (698 occurrences) became 698 cards for 朱 and 708 for 音; **(2)** a single kana is never a word, in katakana as well as hiragana (シ, セ out of a chopped name), and one or two katakana with a katakana neighbour are a fragment too — アイツ (あいつ written for emphasis, so absent from the dictionary) was giving アイ "love" eleven times, while a longer katakana match inside a compound is kept because ゲーム out of ゲームセンター is still the word the reader needs; **(3)** only readings the dictionary says are also a SPELLING join the lexicon (`DictionaryDao.getKanaWrittenReadings`: kana headwords, `uk`, "(usually kana)") — with every reading in it, 俺の**こと** matched 鋸, で**はな**く matched 出鼻 and そう**にな**った matched 担う; **(4)** the さ-stem of する (`される`, `させて`…) is consumed whole as a `GRAMMAR_FORMS` chain, because the deconjugator returns its candidates sorted and さる ("to leave") sorts ahead of する — every 〜されています in the book was a card for 去る. Where several readings of the same stretch are possible the COMMON one is assumed, even at the cost of missing a rare word. `Lexicon.rank()` carries the frequency lists into segmentation and the choice goes: a ranked candidate beats an unranked one (続けている offers the unranked adverb 続けて one step before 続ける, ranked 196), the shallowest derivation wins among ranked ones, and at equal depth the commonest does (あった offers あう, あつ and ある). Above all of it sit the dozen verbs that carry the language (`CORE_VERBS`): the lists rank the KANJI spellings — 在る at 4 553 against 会う at 172 — so numbers alone would read 「〜があった」 as 会う, and ある has to win by name. Two more rules handle the particle that a longest match swallows from either side: a match ending in a case or sentence-final particle is split when what precedes it is a word (今日は → 今日 + は, いいよ → いい + よ), a trailing particle of more than one character is split off the same way when the blend is one no list ranks (上から yes, これから — ranked 249 — no), and a one- or two-character match STARTING with a particle loses to a longer word behind it (「これはしっかり」 was matching はし, 端, ten times a book; はなし is safe because the rule never looks past two characters). Two rules read the frequency lists while segmenting, because the dictionary alone cannot choose between two readings of the same characters: a match ending in a case particle is split when what precedes it is a word (JMdict lists 今日は — it is こんにちは, the greeting — and 今日 was losing 14 of its 27 occurrences to it), and a dictionary entry that is really a frozen inflection (急いで, 頑張って, 知らない, 食べられる, 来た are all entries) gives way to the verb behind it when the corpus calls the entry rare and the verb common. `DictionaryRepository.getCommonSurfaces()` supplies that set (rank ≤ `JapaneseTokenizer.COMMON_RANK`) and an empty one — no frequency dictionary installed — simply turns the preference off. Two guards keep the inflection rules from firing on fragments: an ichidan stem of one kana is refused (「つもりはない」 is は + ない, not the negative of はる, which JMdict lists as a Kansai auxiliary — 37 cards for it in one novel), and an imperative is only read out of a form that is three characters long or carries a kanji (待て, 見ろ — while はよ out of 「事態はより」 was being read as the imperative of はる). `docs/CONJUGATION_MATRIX.md` is generated by `ConjugationMatrixTest` and is the map of what the deconjugator handles: every form of every verb class, built by an independent forward conjugator and put through both the deconjugator and a full scan. Getting it to 512/512 added the bare adverbial く (優しく → 優しい, without which the adverb fell apart into 優 + しく and しく matched 敷く), godan and irregular imperatives, ～ながら/～すぎる/～そう/～なさい on the ます-stem, the spoken contractions (ちゃう, じゃった, とく, ねえ), the r-irregular honorifics (下さいます → 下さる, which used to resolve to いる), よくない → いい, and the ambiguous させられる, which is ichidan for 食べさせられる and godan for 話させられる so both readings are offered. Two ordering facts matter as much as the rules: candidates are sorted by **derivation depth** first (くれます reached くれる in one step and くる in two, and the shorter くる used to win, so "gives me" read as "comes"), and the godan imperative rule is not applied to two-kana forms (され, the stem of される left before a comma, otherwise became さる 17 times). `docs/KATAKANA_ONOMATOPOEIA.md` does the same for loanwords and onomatopoeia.
- **Source sentences**: the tokeniser walks the text sentence by sentence and keeps the first usable sentence (6–90 chars) each word appeared in. `TextScanViewModel.withSourceSentence()` puts it in `WordEntry.exampleSentence` — the first candidate `AnkiCardCreator.pickFrontContextSentence()` looks at — so it lands on the card FRONT under the word, highlighted by the existing `SentenceContextHighlighter`. Nothing in the card builder needed changing; the batch forces `showFrontContextSentence = true` in its copy of the style prefs, because asking for source sentences means asking for that slot regardless of the global card-style setting.
- **Card order** = study order: AnkiDroid introduces new cards in insertion order, so `TextScanPlanner.studyScore()` decides what gets learned first — 0.5 × global frequency rank (log scale), 0.35 × occurrences in the scanned text, 0.15 × how early the word appears. The earliness term is what makes a series scan front-load the words from volume 1.
- **Filtering** (`domain/usecase/TextScanPlanner`): same contract as `JlptDeckPlanner` — fixed rule order, first rejection owns the counter, `selected + skipped == distinct words`. Grammar is dropped by two cooperating rules: the `FUNCTION_WORDS` stoplist (particles, です/ます, する/いる…, plus a closed list of dialogue fillers — まあ, あはは, ふふふ, はぁ — which no tag calls grammar and which four novels put straight into the deck) and the tag-based `WordFilterRules.isFunctionWord`. The stoplist alone was never enough — longest-match segmentation emits compounds (それでも, ということ, かもしれない) that are single dictionary entries and can't be enumerated by hand, but all carry a `conj`/`prt`/`aux` tag. Two things make that tag rule actually fire, and both were broken: `posTokens()` now strips the sense numbers and corpus badges JMdict ships in the same string ("1 prt, ⭐ spec", "⭐ ichi news1k") — they are not parts of speech, and the "every content tag is grammar" test could never pass while they counted as content; and the rule is gated on frequency (`GRAMMAR_KNOWN_RANK`, 3000), because **dropping all grammar is wrong in one direction**: a particle ranked 15 is met on every page, while a construction ranked 8000 is met twice a book and is exactly what the reader does NOT know. Rare grammar becomes a card; the stoplist is the override for basics no frequency list ranks (のか). The stoplist was grown by re-running a real scan and reading the first 200 cards for grammar, four times over — that is the intended way to extend it, with BunPro / Tae Kim's essential grammar as the yardstick for "this is scaffolding, not vocabulary". A separate rule drops one- or two-kana words no frequency list ranks at all: JMdict redirect entries like があ ("see ガー") swallowed the が of 必要がある 65 times in one book. One entry yields one card: two tokens that resolve to the same dictionary entry (the text writes both 持ってくる and 持って来る) are merged, and **the surviving spelling is the one the text used most**, not the dictionary's headword — a lone token gets the same treatment whenever its spelling is one the entry actually has, which is how a card for えっち stops being fronted with JMdict's headword Ｈ — the reader meets the word again in the book's spelling, and a front they never see in the wild is a front they will not recognise. Ties go to the spelling carrying kanji. The stoplist is matched against the WORD rather than the spelling it wears here — katakana folded to hiragana, plus the entry's other written forms — because a narrator who writes himself オレ instead of 俺 was producing a card seen 509 times in one novel. An unranked grammar word is not a rare one: the lists rank とはいえ at 248 980 and ～ごとく at 4 750, so rank 0 means the corpus has no such word at all — a word-plus-particle blend (これは, それを) or a frozen inflection (知らない). Those are gated on how often THIS text uses them (`GRAMMAR_UNRANKED_OCCURRENCES`), which keeps a construction met twice while dropping a blend met twenty times. Grammar the lists DO rank, but past the everyday band, is gated the same way at a higher count (`GRAMMAR_RARE_OCCURRENCES`): 様な — ような written with the kanji, ranked 9 634 — was used 75 times in one book, while とはいえ, ranked far worse at 248 980, appeared twelve. A developer-facing **grammar counter** (`TextScanPlan.grammarUses`) records every structure the text used, with its occurrence count, its global rank and which rule judged it — stoplist, tag rule, or kept-because-rare. It is the instrument for the line this filter has to draw: a kept structure with 80 uses means `GRAMMAR_KNOWN_RANK` is too low for this reader, a stoplisted one with two uses means the list is eating something worth learning. Each row also says whether the structure actually became a card, because `KEPT` only means the grammar rules let it through — 今日は passes them and is then dropped for being ranked 296 050. It renders as a collapsed section on `TextScanScreen` and as a `grammar counter` block in the harness report; nothing downstream reads it. `assumeKnownTopRank` is the other half of "the first hundred cards are stuff I know": frequency-first ordering means the head of every deck is by definition what an intermediate reader already has, and only the user can say where that line is. `knownTokenCount` counts only words skipped as already-in-Anki / already-mined / function words / assumed-known, so the "you already know X% of this text" figure is not inflated by words dropped for being rare.
- **Noise** (`domain/usecase/NoiseRules`, reason `NOISE`, not switchable): words that are not words, kept apart from the grammar stoplist because grammar is *known* and noise is *never*. Rules before list: `isEmphaticNoise` (one kana held down — ああああ; beats — はっはっ; a glottal cut — ちょっ; a stretched stoplisted hiragana word — よー, はー; katakana is exempt from the stretch rule because loanwords spell with ー/ァ), `isBareNumber` (四十, and numeral + counter past 一 — 十人, 三十分; 日/月 are not counters, 二十日 is a word), `isKanaFragment` (hiragana ≤ 3, rank past 3000, a kanji spelling and no usually-kana tag — おり out of なくなっており, にい out of ここにいる), then `BLACKLIST`, where every entry names the book and sentence it came from. The list is grown by running `BookScanHarness` (with `-Danki.fields` so the Anki filter is on) and reading the first 100, then 1000 cards; fix the cause first, blacklist only what no rule separates from a real word. Meant for Kindle Vocabulary Builder input too.
- **Entry resolution** (`domain/usecase/ScanEntryResolver`, shared by `TextScanViewModel` and the harness): written form, then reading, commonest homophone — and Jitendex REDIRECTS are followed (`["⟶ああ", "ああ (redirected from ああっ)"]`), so emphatic and colloquial spellings (ああっ, じーちゃん, ホント, フツー) count as the word itself instead of becoming "⟶" cards. A redirect reached from a lone kanji or from a word opening on っ/ー/ん is a fragment and is dropped, not followed. Word + particle blends whose word is in Anki (自分で, 今から, 静かに) count as already known (`isKnownBlend`). When the book writes a word in kana, the card is fronted with that spelling but the headword stays among the alternatives (`frontedWith`) — dropping it made the Anki check compare kana only.
- **Plain hiragana** (`TextScanFilters.skipPlainKana` + `NoiseRules.isPlainKana`, reason `KANA_ONLY`, a switch on `TextScanScreen`, on when the screen opens): a card needs a spelling that says "vocabulary" — a kanji, katakana (クラス, コンビニ, ムカつく), or a two-mora reduplication (わざわざ, そろそろ; the two morae must differ, or ああああ walks back in). Blunt on purpose: what survives the other rules is nearly all plain hiragana, because the pieces longest match breaks off a sentence are hiragana by nature (それだけ, かと, けし, たん) — and so are the kana adverbs it takes with them (もしかして, とはいえ). Measured on ようこそ実力至上主義の教室へ 1: 4 144 cards with the switch off, 3 721 with it on, 3 254 if kanji alone were required. The default lives in `TextScanViewModel`, not in `TextScanFilters`, so the other rules can still be tested without it.
- **One word, one card** (`domain/usecase/ParadigmMerge` + `JapaneseConjugator.derivedForms`): JMdict files inflections as headwords of their own — 近く is a noun ranked 348, 高さ a noun, 食べたい an entry — so the scanner counted them as words. Two uses of the same generated paradigm: the deck collapses onto its own dictionary forms (`mergeByParadigm`, counts add up), and a form whose dictionary form is in the AnkiDroid collection is "already in Anki" (`isInflectionInAnki`) — which is how 近く finds 近い in a collection the deck never saw. A generated form only counts when it starts with the base's stem (`stemsOf`, with する → し/さ/せ and 来る → 来 spelled out), or する's potential できる would swallow a word of its own. 方 is not an inflection (読み方 is a word people look up), and the spoken negative 〜ん is not read as one either: 盛ん is not an inflection of 盛る. 72 cards in 無職転生 1-2 were inflections of words already in the collection (近く, 早く, 遠く, 大きく, 深み, 怖がる, 使いやすい, 読める).
- **Katakana names** (`JapaneseTokenizer.isRareKatakanaPiece`): katakana is how a story writes its names, and longest match finds dictionary words inside them — グレイラット gave 75 cards for グレイ and 75 for ラット, ルーデウス 222 for デウス, シルフィエット 169 for シルフ. A piece of a longer katakana run — or any match that merely STARTS inside one (シュンと out of バシュンという, キッと out of バキバキッと, デンと out of the town ウィーデン) — has to be a word the corpus ranks inside 20 000 (ゲーム out of ゲームセンター still is); with no frequency list installed the rule stands down, which is what `Lexicon.ranksAvailable` is for. A lone kanji straight after katakana is a compound's tail (ミグルド族, パンク系, バス停). 様 counts as an honorific after a token of two characters or katakana (エリス様 yes, 神様 no).
- **Names** (`TextScanPlanner.isNameOnly`): a novel names people with words the dictionary also lists, and the honorific is the only thing that tells them apart — `JapaneseTokenizer` counts how often each word is followed by くん/さん/ちゃん/先輩/先生/氏. What happens next is deliberately asymmetric: 池 is a classmate AND a pond the frequency lists rank at 3 770, so the card stays (the reader will meet that word elsewhere), while 平田 is a classmate and nothing else — no list ranks it — so it goes. The tempting shortcut, "unranked and frequent means a name", would have thrown away 指導室 and 敷地内, unranked compounds used ten times each in the same book.
- **Shared rules** (`domain/usecase/WordFilterRules`): the archaic, proper-name and function-word tag rules; both planners answer the same question about the same data, so they share one implementation. All three are "all tags, not any": a merged entry carries every sense's tags, so 自分 (`pn` + `n`) and a word JMnedict also lists as a surname must survive. Inflection paradigms and bare `exp` are neutral — they say how a word conjugates or that it is a phrase, never what it is.
- Cards are tagged `yomitan-mobile`, `text-scan` and a slug of the file name, and — like the JLPT generator — are NOT written to `exported_words`.
- `FrequencyTier` (`domain/model/`) is the one definition of the Top-1K…Top-50K bands, shared by the scanner's range chips and the frequency badges on `WordEntry`/`MergedWordEntry`.
- **Offline harness** (`app/src/test/.../tools/BookScanHarness.kt`): runs the whole pipeline on a desktop JVM over real files — the app's own `YomitanDictionaryParser` on a downloaded JMdict/frequency zip stands in for Room, everything downstream is the production code. Skipped unless `-Dbook.paths=…:… -Ddict.zip=… -Dfreq.zip=…` are passed (the test task forwards those properties; see `testOptions.unitTests`). Its report includes a `grammar suspects` section, which is how the stoplist above gets extended. It cannot see AnkiDroid, so the duplicate filters are off there.
- **Kindle sync** (`tools/kindle-sync/` + `tools/KindleSync.kt`, design notes in `docs/kindle_thoughts.md`): Vocabulary Builder lookups → Anki desktop through AnkiConnect, on the same resolver/indexer/card builder, run like the harness. The Paperwhite is MTP and KDE's kio worker holds it, so `vocab.db` comes off through `kioclient`, not libmtp. Cards match the phone's: `rebuildFields` with the phone's backup `settings.json` (pulled over adb; random fonts read off recent notes otherwise), the catalogue's pitch/KANJIDIC zips, locale `pl`, and VOICEVOX standing in for Android TTS — given the reading with the kanjium accent written in, not the headword (Open JTalk is only the fallback: its HMM voice was the "terrible sound" complaint). `kindle-watch.service` (user unit, `udevadm monitor`, no root) runs it on plug-in. Each run syncs AnkiWeb before (a failure aborts; the duplicate check needs a current collection) and after, and in between applies the user's AutoReorder add-on — restated over AnkiConnect because the add-on only runs at Anki start, with its config read from the add-on's own `meta.json`.
- **PDF is not supported**: Android has no text-extraction API (`PdfRenderer` only rasterises), so it would need a third-party parser. `TextFileReader` rejects PDFs with a clear message rather than pretending.

### Result merging
`MergedWordEntry.mergeEntries()` groups `WordEntry` items by `(expression, reading)`. Within each group it picks the primary (prefers kanji + lower frequency rank), merges definitions, and collects alternatives. This avoids homophone grouping errors. Dedup of the gloss list and remapping of each example's `definitionIndex` onto the merged positions happen together in `mergeDefinitionsAndExamples()` — so the detail screen and Anki export can group examples by `definitionIndex` and trust it, with no compensation logic of their own.

### Utils (`util/`)
- `InputSanitizer`: sanitizes FTS queries and Anki card content
- `JapaneseDeconjugator`: rule-based, no external library
- `RomajiConverter`: romaji → hiragana conversion for search
- `WordCategoryClassifier`: classifies entries into JLPT/POS categories using JMDict tags
- `JlptLevelUtil`: JLPT level from JMDict tags with expression-level fallback
- `SentenceContextHighlighter`: highlights target word inside an example sentence

### Card style preferences
`data/settings/CardStylePreferencesReader.kt` is the ONLY path from stored settings to an exported card — the card-style screen keeps its own copy for the preview. A preference the screen writes but the reader does not read is a switch that changes the preview and nothing else (this happened to `card_show_word_divider`); `CardStylePreferencesReaderTest` fails when that happens again. The reader also validates colours and font names, because `BackupManager.importSettings` accepts any DataStore key from a user-picked JSON and those values are interpolated into the CSS and HTML written into the AnkiDroid collection.

### DI (`di/`)
Three Hilt modules: `AppModule` (singleton services), `DatabaseModule` (Room + DAOs), `RepositoryModule` (binds interface → impl).

### Widgets (`widget/`)
`SearchWidgetProvider` reaches the singleton DAO graph through the Hilt `WidgetEntryPoint` (`EntryPointAccessors.fromApplication`) instead of building its own Room instance. `QuickSearchWidgetProvider` touches no database.

## Known issues
- Many strings are hardcoded in Compose screens as inline `tr(pl, en)` bilingual literals rather than `strings.xml` resources. This is the app's deliberate i18n strategy (EN/PL only, driven by `LocaleHelper`), not a bug — but it means adding a third language would require a real resource migration.
