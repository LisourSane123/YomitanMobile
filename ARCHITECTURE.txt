----------------------------------------------------------------------
1. THREE-LAYER PROJECT (data / domain / ui), wired with Hilt
----------------------------------------------------------------------

domain/
  - Pure Kotlin. No Android, no Room, no kotlinx.serialization in
    public APIs. Models: WordEntry, MergedWordEntry, ExamplePair,
    AnkiCard, CardStylePreferences, CardSection (back-side
    section ordering), ImportProgress, ImportResult.
  - DictionaryRepository is the only abstraction boundary. Use
    cases (SearchDictionaryUseCase, GetWordDetailUseCase,
    DictionaryManagementUseCases) sit above it.

data/
  - data/local: Room DB (AppDatabase v14) + DAOs.
  - data/parser: streaming Yomitan ZIP parser (term banks, kanji
    banks, term meta banks).
  - data/repository: DictionaryRepositoryImpl — wraps DAOs and parser.
  - data/anki: AnkiCardCreator integrates with AnkiDroid via
    AddContentApi + raw content provider for CSS/template updates.
  - data/download: dictionary catalog and download manager.
  - data/ai: AiProvider enum + AiSummaryService (HTTPS-only client
    for Gemini / DeepSeek / OpenAI-compatible chat completions). See
    section 11.
  - data/sentence: gone — removed alongside the online Tatoeba
    fallback. Sentence column is now: Jitendex examples →
    SentenceDao seed → empty.

ui/
  - Jetpack Compose + MVVM. Each screen has a paired ViewModel.
  - Navigation: ui/navigation/AppNavHost.kt with sealed Screen routes.
  - Localization: util/LocaleHelper.isEnglish(config). Each screen has
    `val isEnglish = LocaleHelper.isEnglish(LocalConfiguration.current)`
    and an inline `tr(pl, en)` helper.

di/
  - AppModule (singletons), DatabaseModule (Room + DAOs +
    performance PRAGMAs in onOpen), RepositoryModule (interface →
    impl bindings).

2. SEARCH PIPELINE
----------------------------------------------------------------------

Trigger: SearchScreen text input → SearchViewModel.onQueryChanged.

JP path:
  SearchViewModel
    → JapaneseDeconjugator.candidateForms(query) — rule-based
      generator, cap 24 candidates, depth 3
    → SearchDictionaryUseCase.invokeWithAlternatives(query, candidates)
    → All queries run in parallel (coroutineScope { async }):
         • literal query (index 0): repository.searchCombined(q)
           → DictionaryDao.searchCombined (exact + prefix-LIKE)
         • each deconjugation alternative: repository.searchExact(q)
           → DictionaryDao.searchExact (exact expression/reading only —
             prefix-LIKE would drag in unrelated longer words that merely
             share the base-form prefix, e.g. 見る → 見るに値する)
    → Merge by entry id (literal query wins; alternatives capped at 20)
  → SearchViewModel applies MergedWordEntry.mergeEntries
    (groups by (expression, reading), picks primary by kanji + freq)
  → JlptVocabulary fallback runs per merged entry where jlpt_level == 0
  → UI renders MergedWordEntry list

EN mode:
  SearchDictionaryUseCase.invokeEnglish → repository.searchByDefinition
  → FTS over the `definition` column (JSON-encoded gloss list).

Romaji mode:
  RomajiConverter.convert(romaji) → hiragana → JP path.

Debounce: 100 ms inside SearchViewModel before kicking off a search.

Performance note: invokeWithAlternatives now runs the candidate searches
in parallel inside coroutineScope { ... async }, then merges by entry id
with the original query taking priority (audit issue (c) — RESOLVED).
The single per-candidate `first()` in the lambda is the only suspending
call; all candidates run concurrently.

3. DICTIONARY IMPORT (Yomitan ZIP format)
----------------------------------------------------------------------

Trigger: DictionaryDownloadScreen / SetupScreen calls
DictionaryManagementUseCases → repository.importDictionary(stream).

Repository.importDictionary:
  beginBulkImport()           — PRAGMA synchronous=OFF + journal=MEMORY
  parser.parseFromZipStreaming(...)
    callbacks emit:
      onBatch (terms)         — batched insertAll into dictionary_entries
      onMetaBatch (freq, pitch) — frequency / pitch updates
      onJlptBatch             — JLPT level updates
      onKanjiBatch            — kanji_entries inserts
  rebuildFtsIndex
  endBulkImport()             — restore synchronous=NORMAL + journal=WAL

Parser layout detection (YomitanDictionaryParser.parseTermEntry):
  • term[2] definitionTags, term[3] rules, term[7] termTags
  • term[5] definitions: tries Jitendex sense-aware structure first
    (sense-groups → sense-group → POS span + ol of li[sense]),
    falls back to flat parseDefinitions for plain JMDict.
  • Rt/rp ruby readings stripped from text extraction so example
    sentences don't show "食たべる" mid-sentence.
  • POS codes (v1, vt, …) read from <span data-content="part-of-speech-info">
    and combined with rules.

JLPT detection paths (priority order at lookup):
  1. tag-based: jlpt-1..jlpt-5 in definitionTags/termTags →
     JlptLevelUtil.extractAsInt at parse time, written to jlpt_level.
  2. companion meta-bank (yomitan-jlpt-vocab): freq channel with
     value=-1 + displayValue="N1".."N5" → routed to JlptUpdate /
     updateJlptLevelBatch (only updates rows where jlpt_level == 0).
  3. JlptVocabulary curated list, applied at view time
     (DetailViewModel/SearchViewModel) when jlpt_level is still 0.

Schema invariants:
  • dictionary_entries has examples_json column (DB v11) holding
    List<ExamplePair> with definitionIndex.
  • dictionary_entries has jlpt_level column (DB v10).
  • word_frequencies table (DB v14) holds one row per (expression, reading,
    dictionary) with rank + display_value — the per-source frequency store.
    See section 12. dictionary_entries.frequency is still written during
    import but now holds the BEST (lowest) rank across all installed lists
    (DictionaryDao.updateFrequencyBest*), used only for search ordering.
  • dictionary_entries_fts is a Room-managed FTS4 external-content
    table; it auto-syncs via triggers on every insert/update.
    Bulk-import path still works because the rebuild at the end
    handles any drift.

Performance dials (bulk import):
  parser.BUFFER_SIZE                   = 256 KB
  repository.batchSize                 = 10000
  repository.beginBulkImport pragmas   = synchronous OFF, journal MEMORY

4. ANKI CARD EXPORT
----------------------------------------------------------------------

Entry point: DetailViewModel.exportToAnki → performExport.

Sentence-source priority (after the online-Tatoeba removal):
  1. entry.examples (Jitendex, attached per gloss via definitionIndex)
  2. local SentenceDao seed (~22 hardcoded rows, migration v8 → v9)
  → empty. Mustache `{{#Sentence}}…{{/Sentence}}` collapses the whole
  block (including the trailing <hr>) when no source supplies one.

FIELD_NAMES (10 fields, order matters — AnkiCard.toFieldArray
mirrors it):
  Front, FrontContext, Reading, Meaning, PitchAccent, Frequency,
  Audio, Sentence, KanjiBreakdown, Summary.

Meaning field structure (formatMeaningForCard):
  <div class="pos-line">ichidan verb, transitive verb</div>
  <ol class="meanings">
    <li class="meaning-item">
      <span class="gloss">to eat</span>
      <div class="meaning-ex">
        <div class="meaning-ex-jp">…</div>
        <div class="meaning-ex-en">…</div>
      </div>
    </li>
    …
  </ol>

Sentence field: only renders unattached examples (those with
definitionIndex < 0). Jitendex-sourced examples never duplicate here.

FrontContext field: the highlighted context sentence on the card front is
populated for EVERY word when the showFrontContextSentence preference is on
(default true). The old hiragana-only gate was removed — kanji words get a
front sentence too, and .context-highlight now underlines (plus bold/tint) the
matched target so the word is visibly marked whenever the highlighter finds it.
  Highlighting (SentenceContextHighlighter.buildHighlightedSentenceHtml):
  the preferred tokens (expression, reading) are each expanded through
  util/JapaneseConjugator.inflectedForms — the forward counterpart to
  JapaneseDeconjugator — so a sentence that uses the word in a conjugated
  shape (dictionary たべる vs. sentence たべた) is still matched. All
  candidate surface forms are tried LONGEST-FIRST, so the fullest occurring
  inflection wins (たべている over a bare たべ prefix) and absent forms are
  skipped. る-final words emit both ichidan and godan paradigms (ambiguous
  from kana alone); only the form present in the sentence ever matches.
  する / くる / i-adjectives are handled as special cases. Output stays
  HTML-escaped. Covered by JapaneseConjugatorTest +
  SentenceContextHighlighterTest.

Header layout (top of the back side, fixed — not part of the
reorderable section list):
  expression
  .word-divider <hr>   ← full-width 1px white rule between expression
                          and reading
  reading
The Frequency field is still part of FIELD_NAMES (model schema is
unchanged at v8) but the header no longer renders it — users asked
for a cleaner header.
Followed by an unconditional full-width <hr> (the "layer divider")
that separates header from the reorderable sections below.

Dynamic back template (AnkiCardCreator.buildBackTemplate):
  • The reorderable sections (PITCH, SUMMARY, MEANING, SENTENCE,
    AUDIO, KANJI) come from CardStylePreferences.sectionOrder, which
    is the user's pick from CardStyleScreen and persisted as a
    comma-separated CardSection list under CARD_SECTION_ORDER.
  • Every section ends with its own trailing <hr>; CSS rule
    `.back > hr:last-of-type { display: none }` hides the dangling
    last divider regardless of order.
  • Meaning is the only section that's rendered unconditionally — all
    others are wrapped in `{{#Field}}…{{/Field}}` so empty data
    collapses the whole block.
  • CARD_BACK_TEMPLATE constant is the static fallback (default
    order) used by tests / previews. Real exports go through
    buildBackTemplate(stylePrefs.sectionOrder) in addNote.

AnkiDroid model:
  MODEL_NAME = "Yomitan-Mobile-v8"   — bumped from v7 when the Summary
  field was added. NEVER bump unless FIELD_NAMES changes again.
  Earlier names (v7, v4, the bare "Yomitan-Mobile") are listed in
  modelNamePriority so they're still discoverable as legacy fallbacks
  if the user reverts. CSS and template updates flow to existing v8
  models via the content provider (updateModelCss /
  updateModelTemplates), so layout / order changes apply
  retroactively to all v8 cards.

Template push diagnostics:
  updateModelTemplates inspects rows-affected from
  contentResolver.update and now returns Boolean. On rows == 0 (older
  AnkiDroid silently dropping template writes) it logs and returns
  false; getOrCreateModel then falls through to createCompatibleModel
  with skipPrimaryName = true, which spawns the next free
  Yomitan-Mobile-v8-N variant whose template matches the current
  section order. Pre-existing cards stay valid on the original model;
  new exports land on the variant. Modern AnkiDroid (where the write
  succeeds) keeps using the single canonical model — no orphans.

5. CARD STYLE PREFERENCES
----------------------------------------------------------------------

Stored in DataStore (keys defined in MainActivity companion).
Loaded by CardStyleScreen (for editing) and DetailViewModel (for
export). CardStylePreferences data class is the in-memory shape.

Toggleable bits that reach the CSS via buildCssFromPreferences:
  • showPitchAccent / showFrequency / showSentence / showFrontContextSentence
  • showSectionDividers — controls `hr { display: none }`
  • randomFontsEnabled / randomVoicesEnabled (export-time random pick)

Section ordering:
  • sectionOrder: List<CardSection> — reorderable back-side blocks
    (PITCH, SUMMARY, MEANING, SENTENCE, AUDIO, KANJI). Persisted as a
    comma-separated string under CARD_SECTION_ORDER and decoded by
    CardSection.decode. Decode is forgiving: missing sections get
    appended at the end, unknown tokens are dropped, duplicates
    collapse — so saves from older app versions keep working when a
    new section is added.
  • Header (expression + freq + reading) is NOT part of sectionOrder
    — it's pinned at the top.

AI summary fields (see section 11):
  • aiSummaryEnabled, aiProvider (AiProvider enum), aiApiKey,
    aiPrompt, aiModel.

Legacy / removed prefs (still keys in older devices' DataStore but
no longer read by code — functionally inert):
  • onlineSentenceApiConsentGranted, sentence_api_consent_granted
  • useOnlineSentenceApi, card_use_online_sentence_api

7. LOCALE HANDLING (EN ↔ PL)
----------------------------------------------------------------------

util/LocaleHelper.isEnglish(config) walks the LocaleList top-to-
bottom: returns English the first time it sees `en`, Polish the
first time it sees `pl`, English fallback otherwise. Replace any new
inline `locales.get(0).language.equals("en", true)` checks with
this helper.

Strings are inline `tr(pl, en)` calls — there's a values/strings.xml
+ values-pl/strings.xml pair for the few strings that are accessed
from the manifest (app_name etc.) but most UI text is hardcoded in
Compose. Leave it alone unless you are doing a full i18n migration.

11. AI SUMMARY INTEGRATION
----------------------------------------------------------------------

Optional per-export call to a third-party LLM that fills the back-side
Summary slot (rendered between PitchAccent and Meaning by default —
position is reorderable like every other section).

Components:
  data/ai/AiProvider.kt
    Enum of supported providers: GEMINI ("gemini-3.1-flash-lite"),
    DEEPSEEK ("deepseek-chat"), OPENAI ("gpt-4o-mini"). Stable
    storageValue strings keep DataStore round-trips robust against
    display-name renames. AI_DEFAULT_PROMPT is a template with
    {expression}, {reading}, {meaning}, {language} placeholders.

  data/ai/AiSummaryService.kt
    Single suspend entry point: generateSummary(provider, apiKey,
    promptTemplate, word, reading, meanings, language, modelOverride).
    Dispatches to callGemini (POST .../generateContent?key=…, body
    `{contents:[{parts:[{text:…}]}]}`) or callOpenAiCompatible (POST
    chat/completions, body `{messages:[{role:"user", content:…}]}`,
    Authorization: Bearer KEY). Both flow through postJson, which
    returns an HttpResponse(statusCode, body) — the status code
    is the part rateLimitFailure / friendlyError use to surface
    helpful messages.
    Returns sealed AiSummaryResult: Success(text) / Failure(message) /
    Disabled. Failures NEVER throw out — Anki export must keep working
    even when the AI provider is unreachable.
    Network-allowlist:
      generativelanguage.googleapis.com, api.deepseek.com, api.openai.com.
    Response size cap: 256 KB.

  CardStylePreferences AI fields:
    aiSummaryEnabled / aiProvider / aiApiKey / aiPrompt / aiModel
    (override; blank → provider.defaultModel). DataStore keys:
    CARD_AI_SUMMARY_ENABLED, CARD_AI_PROVIDER, CARD_AI_API_KEY,
    CARD_AI_PROMPT, CARD_AI_MODEL.

  DetailViewModel.performExport
    Calls aiSummaryService.generateSummary only when
    aiSummaryEnabled && aiApiKey is non-blank. Failures emit
    DetailEvent.AiSummaryFailed → DetailScreen renders a snackbar
    "AI summary failed: <message>". The card export continues with
    an empty Summary field, which the {{#Summary}} mustache block
    hides automatically.

  AnkiCardCreator integration:
    createAnkiCard accepts aiSummaryText: String. The text is
    HTML-escaped (third-party LLM output) and rendered in
    .summary-section via `white-space: pre-wrap` so multi-line
    responses preserve their breaks.

12. FREQUENCY LISTS (multi-source)
----------------------------------------------------------------------

A word can carry a frequency rank from several installed lists at once
(e.g. JPDB for media/colloquial, BCCWJ for formal written). Each list's
rank is kept separately and shown side by side.

Storage:
  • entity/WordFrequency (table word_frequencies, DB v14): one row per
    (expression, reading, dictionary) → rank + display_value. reading is
    "" when the source shipped none; lookups match the exact reading OR
    the empty-reading fallback (FrequencyDao.getForWord).
  • dictionary_entries.frequency still exists but now holds the BEST
    (lowest) rank across ALL lists, written via
    DictionaryDao.updateFrequencyBest* (only lowers / fills 0). It is used
    only for search ORDER BY — never for display.

Import (DictionaryRepositoryImpl.importDictionary):
  • Parser emits FrequencyUpdate(expression, reading, frequency,
    displayValue). displayValue comes from parseFrequencyDisplayValue
    (rank-based lists ship one; plain numeric lists leave it "" and the
    repository falls back to the rank string).
  • The index.json title isn't reliably known mid-stream, so freq rows are
    written under the temp name "temp" and renamed to the real title at the
    end (frequencyDao.updateDictionaryName) — same pattern as term/kanji
    banks. A prior import of the same list is deleted first (re-import
    replaces). deleteDictionary also clears word_frequencies.

Display:
  • repository.getFrequencies(expr, reading) → List<WordFrequencyInfo>.
  • DetailViewModel.loadFrequencies orders them via
    WordFrequencyInfo.order(list, priority, showAll): priority is the user's
    ordered list of dictionary titles (DataStore FREQUENCY_DISPLAY_ORDER);
    lists not in priority fall to the end keeping input order; showAll=false
    (DataStore FREQUENCY_SHOW_ALL) collapses to the single top list.
  • DetailScreen renders them as FlowRow chips (WordFrequencyInfo.label() =
    "<dict> #<rank>"). Falls back to the legacy MergedWordEntry.frequencyLabel
    star-bucket text only when no per-source rows exist (pre-re-import words).

Settings:
  • ui/settings/FrequencyDisplayScreen + FrequencySettingsViewModel: a
    show-all switch and an up/down reorderable priority list, fed by
    FrequencyDao.observeDictionaries() (the installed lists). Newly installed
    lists append; uninstalled ones drop. Reached from SettingsScreen via
    onNavigateToFrequencyDisplay → Screen.FrequencyDisplay.
